# Configuration reference

Every setting Yellow Jack reads, what it does, and what it defaults to.

**Where settings can come from — and can never come from — is a separate, asserted invariant:**
see [CONFIG_SURFACE.md](CONFIG_SURFACE.md). Configuration is read from the **process environment
only**; nothing is discovered from a working directory, a request path, or inspected package
content. That document is the deliverable of issue #38 and is kept honest by tests.

This file is the deliverable of **issue #51 acceptance item 1**: *the current `FW_*` surface
enumerated with a one-line justification per knob, and the count stated as a defended budget.*
It now covers **every service**, not only the firewall — the approval service, console,
scheduler, scanner and cache each have their own section below, and all of them are
drift-checked by `configreference_test.go`.

---

## The budget, stated

**40 environment variables. 0 of them are required.** — the FIREWALL's surface, which is
what issue #51 asked for and what the budget argument below defends.

**The whole stack: 89 environment variables across six services. Still 0 required to
start.** Every service comes up with nothing set — the approval service falls back to an
in-memory store, the console to loopback with no auth, the scheduler to the local docker
CLI. The only genuinely required variables in the surface are `SCANNER_REPO` and
`SCANNER_SINK_URL`, and those are set by the scheduler on a container it launches, never
by an operator.

⚠️ **One exception, added by #22: the shipped `docker-compose.yml` requires
`POSTGRES_PASSWORD`.** No *service* requires it — the sentence above still holds for every
binary — but the compose file interpolates it rather than carrying a literal, because a
default there is one identical database credential on every installation. It stays a
zero-friction start for the documented path: `sh scripts/dev.sh up` generates a per-machine
value into a git-ignored `.env` first. A bare `docker compose up` on a fresh clone fails,
by design, with an error naming that command. Quote "0 required" of the SERVICES; do not
quote it of a raw `docker compose up`.

⚠️ **"0 required" is a statement about STARTING, not about running well.** A real
deployment sets `APPROVAL_DATABASE_URL` — without it the approval queue and the audit
trail live in memory and are lost on restart, which is wrong for anything holding a
compliance record. And a console reachable beyond loopback needs `CONSOLE_AUTH_USER` /
`CONSOLE_AUTH_PASS` (or the `CONSOLE_OIDC_*` set, which supersedes them), because those are
its only access control. Quote "0 required" as
the friction claim it is; do not quote it as "no configuration needed".

The second number is the one that matters. Issue #51 exists because *"adopting Yellow Jack must
cost less than routing around it — one `.npmrc` line, no new client tooling, no workflow change"*,
and for a cooperative-client gate friction is not a UX problem but a **coverage** problem: a
developer who finds the gate annoying routes around it, and our dashboard stays green while the
traffic leaves.

A container started with **no environment set at all** comes up as a working npm firewall.
`FW_ECOSYSTEM` defaults to `npm`, `FW_UPSTREAM` derives from the chosen ecosystem so the two
cannot be mismatched, and `FW_LISTEN_ADDR` defaults to `:8080`. Every other knob has a default
chosen to be safe rather than permissive.

**An honest note on the count.** Issue #51 was written when the surface was about five knobs, and
named sprawl as the thing to avoid. We are at 31. That is not undefended sprawl — the argument for
each addition sits in `config.go` itself, and `FW_SCORE_CACHE_MAX_ENTRIES` carries a whole
paragraph on why it is **one** knob covering two caches rather than two. What had never happened
is the enumeration and the total, which is what this file is. **Read 31 as a number to defend from
here, not as a clean bill of health.**

**The rule for adding one:** justify it against this budget in its own doc comment, and update the
count above. `TestConfigReferenceIsComplete` fails if a `FW_*` variable exists in `config.go` and
is not listed here, so the two cannot drift silently.

## Deployment

| Variable | Default | What it does |
|---|---|---|
| `FW_LISTEN_ADDR` | `:8080` | The address:port this service listens on. |
| `FW_ECOSYSTEM` | `npm` | Which ecosystem this instance gates: `npm`, `pypi`, `oci`, `maven`. One process serves one ecosystem. |
| `FW_UPSTREAM` | derived from ecosystem | The real registry allowed requests are proxied to. The default tracks `FW_ECOSYSTEM` so the two cannot be mismatched. 🛡️ **It holds exactly ONE registry, and that is load-bearing.** With a single upstream there is no "not found here, try the next one" step — so the gate **cannot** resolve an internal package name to a public registry, which is the dependency-confusion substitution described in the `FW_DENY_LIST` row below. That protection is a side effect of this field being single-valued rather than something anyone designed, which is precisely why it is written down here: **an ordered list of upstreams with not-found fallback would make this gate the resolver that performs the attack.** If multiple upstreams are ever added, internal-first ordering and a rule that a claimed-internal name never falls through are requirements, not refinements. |
| `FW_PUBLIC_URL` | derived from the Host header | Externally reachable base URL of *this* proxy, used when rewriting artifact URLs so those fetches come back through us. **TLS-fronted deployments must set it.** It must be reachable **from where the client runs**, not from where the proxy runs — see the note below. |
| `FW_FILES_UPSTREAM` | `https://files.pythonhosted.org` | PyPI only: the host serving artifact bytes, which is not the index host. |
| `FW_TRUSTED_PROXIES` | *(empty — trust none)* | CIDRs or IPs whose `X-Forwarded-For` is believed when recording a pull's source IP. Empty is correct unless you genuinely sit behind a proxy you control. |
| `FW_INTERCEPT_LISTEN` | *(empty — off)* | **TLS-interception mode** (D51: optional, sysadmin-deployed). A second listener that accepts `CONNECT`, terminates the client's TLS with a certificate minted from `FW_INTERCEPT_CA_FILE`, and hands every request to the **same gate** the cooperative path uses — one policy, one refusal path. It terminates TLS **only for the hostname of `FW_UPSTREAM`** and refuses `CONNECT` to any other host without dialling it, so the mode adds **no egress destination** (see `docs/EGRESS.md`). Under interception the packument is relayed **verbatim** (no `dist.tarball` rewrite), so lockfiles keep the registry's own URLs. All four ecosystems. **PyPI**: it also terminates TLS for the hostname of `FW_FILES_UPSTREAM`, and binds each wheel to the package whose relayed index listed it — a wheel URL no relayed index listed is refused. **OCI**: the token realm the registry names in its 401 is rewritten to `/_token` on the registry host and relayed from there, and blob CDNs are followed by the gate, so the client never needs a second host. **Maven**: the repository path in `FW_UPSTREAM` (`/maven2`) is stripped from intercepted requests so the gate sees the same paths it gates as a mirror, and a request on the registry host outside that path is refused without a dial. The Maven default is `https://repo.maven.apache.org/maven2` — the name Maven's own super-POM and Gradle's `mavenCentral()` carry — so an unconfigured client's `CONNECT` is accepted without an operator step. Central also answers to `repo1.maven.org`; point `FW_UPSTREAM` at *that* name and every `CONNECT` is refused with both hosts in the log, because the listener terminates for the name you configured and not for the one the client says. The same is true of any registry reachable under two names. A registry served under a path gets the same stripping whatever the ecosystem. Point clients at it as their HTTPS proxy (`HTTPS_PROXY` / `npm_config_https_proxy`) and distribute the **root** they must trust yourself (`NODE_EXTRA_CA_CERTS` for Node, `SSL_CERT_FILE` for pip, uv and Go clients such as crane, `certs.d/<registry>/ca.crt` for the Docker daemon, `keytool -importcert -cacerts` for Maven and anything on the JVM, which reads neither the OS store nor `SSL_CERT_FILE`; Maven takes its proxy from `settings.xml` `<proxies>`, not `HTTPS_PROXY` — each measured in `docs/TLS_INTERCEPTION.md` class 1); a client that does not trust it is logged as *"does not trust our CA"* with its address. Must be set together with `FW_INTERCEPT_CA_FILE`. |
| `FW_INTERCEPT_CA_FILE` | *(empty)* | **Absolute** path to a PEM file holding the CA certificate the listener signs per-host certificates with — in practice an **intermediate issued by your own PKI, never the root** (D105: we never hold the root key — ⚠️ D105's text is UNRECOVERED, see `TLS_INTERCEPTION.md`; the practice is well attested and the product is built to it, but it is a reconstruction, not decision text) — plus its private key, plus any chain to present. How to produce this file from a CA you run, with a verified recipe: `docs/CA_INTEGRATION.md`. Must be a CA (`basicConstraints CA=TRUE`, `keyCertSign`) and in validity; anything else is refused at startup with the reason, before any listener binds. Per-host leaves are P-256 and reused for 24h, so a rotated intermediate takes effect within a day. Read once at startup. **Trust preflight:** at startup the listener also mints a certificate for every host it will terminate for and verifies it as a client holding only the file's *last* certificate would; a chain no client could build (the wrong root behind the intermediate, an issuing CA name-constrained to your corporate domain or without `serverAuth`) is refused at startup with the verifier's reason, and the startup line names the certificate clients must hold with its SHA-256 fingerprint (`openssl x509 -fingerprint -sha256` form) to compare with what you distributed. It does not claim any client trusts it — that is each client's store (`docs/TLS_INTERCEPTION.md` class 1). |

> **Behind a TLS terminator `FW_PUBLIC_URL` is REQUIRED.** Unset, artifact links are minted as
> `http://` + `Host`, which behind a terminator is the right host with the wrong scheme; the
> gate does not read `X-Forwarded-Proto`. Measured with a real `npm install`, which fails on
> the artifact fetch. See "Serving the gate over HTTPS" in `docs/SETUP.md`.
>
> **`FW_PUBLIC_URL` is an address for the CLIENT, and the failure is confusing.** The proxy
> mints artifact URLs from this value and hands them to the package manager, which then
> fetches them *itself*. So the value has to resolve from wherever that client runs.
>
> Measured while writing the reference deployment: with `FW_PUBLIC_URL=http://localhost:8080`
> and a containerised `npm`, metadata fetches succeed and the install then dies with
> `ECONNREFUSED` on `http://localhost:8080/_tarball/...` — a URL that reads as perfectly
> correct in the error message. The container resolved `localhost` to itself. Pointing it at
> the address the client uses (`http://firewall:8080` on that network) installs cleanly.
>
> The rule: `localhost` is right when the client is on the same host as the proxy, and wrong
> the moment it is not. Leaving it unset is worse in a different way — URLs are then minted
> per request from the `Host` header, so one dependency resolves differently per environment
> and that difference is recorded in developers' lockfiles. The proxy warns at startup when
> it is unset.

## Scoring

| Variable | Default | What it does |
|---|---|---|
| `FW_SCORECARD_MODE` | `stub` | How a score is obtained: **`off`** (no scoring at all), `stub` (fixed, offline dev), `api` (deps.dev), `local` (scan on demand via the scheduler).<br><br>**`off` is the mode for running the gate on the operator lists, the known-malware feed and the release-age window alone** (D273/D280: OSSF scanning is *optional* for the open-source launch). It short-circuits **above** the repo lookup, so it makes **no network call** for scoring and works in an air-gap; a package nothing else refuses is served, with the reason saying so rather than claiming a score it never took. It is a **supported, ready** configuration, and **the console treats it as one**: with every replica reporting `off`, `/lookup` drops its Score section and `/audit` its Score/Threshold columns rather than showing a scanner that was never asked (D273, `#151`). A mixed fleet, or a replica that does not report its mode, keeps them.<br><br>⚠️ **`stub` is a development fixture and now reports NOT READY** (`/readyz` 503, D273/#141). It does not decline to score — it asserts a flat 7.5 for **every** repository, which is worse than not scoring, because the verdict looks like a measurement. It remains the default only so existing dev setups do not change behaviour silently; **use `off` for a deployment that has no scanner.** |
| `FW_SCORE_THRESHOLD` | `5.0` | Minimum OpenSSF Scorecard score (0.0–10.0) to allow. Below it, blocked. |
| `FW_SCANNER_URL` | *(empty)* | Base URL of the scheduler service. Required **only** when `FW_SCORECARD_MODE=local`. |
| `FW_SCORECARD_REQUIRED_CHECKS` | *(empty = default set)* | The coverage floor for a **partial** Scorecard report (#133, D271), `local` mode only. Scorecard exits non-zero when one check hits a runtime error and still writes a complete report whose aggregate *excludes* the errored checks; the gate salvages it. A partial report is compared to `FW_SCORE_THRESHOLD` **only if every check named here scored**; if a required check errored, the package is unscorable and the refusal names the check. Comma-separated Scorecard check names. The default is every check Scorecard's own documentation marks Critical or High: `Dangerous-Workflow, Webhooks, Binary-Artifacts, Branch-Protection, Code-Review, Dependency-Update-Tool, Maintained, Signed-Releases, Token-Permissions, Vulnerabilities`. `none` disables the floor, so any partial report is accepted on its aggregate. A **count** is deliberately not offered: losing `Dangerous-Workflow` and losing `License` are not the same event. |
| `FW_DEPSDEV_BASE` | deps.dev | Base URL of the deps.dev API, used for both api-mode scoring and the repo cross-check. Configurable for mirrors and air-gapped installs. |
| `FW_VERIFY_REPO` | `true` | The deps.dev package-to-source-repo cross-check, so a package cannot borrow a high-reputation repo's score. |
| `FW_UPSTREAM_AUTH` | *(empty)* | `Authorization` value sent on the firewall's **own** probe requests, scoped to the upstream host so it cannot leak to deps.dev or the approval service. |
| `FW_UPSTREAM_AUTH_FILE` | *(empty)* | The same `Authorization` value, read from a **file** and re-read as it changes, so a **short-lived** upstream token (AWS CodeArtifact, Chainguard) is picked up without restarting. Mutually exclusive with `FW_UPSTREAM_AUTH` — setting both is refused at startup. A failed or empty read keeps the last good value rather than silently going anonymous.<br><br>⚠️ **Bind-mount this file's DIRECTORY into the gate — never the file.** The whole point of this variable is rotation, and a file bind mount defeats it: the mount pins that file's *inode*, and every credential helper that writes safely (temp file, then rename — AWS CLI, Vault agent, Kubernetes secret projection) replaces the inode, so the container goes on reading the **old token forever**. Note that the "keeps the last good value" property above does **not** save you here: the read does not fail, it succeeds and returns stale bytes. The symptom is an expired upstream credential with **no error anywhere**, and it is **platform-masked** — Docker Desktop resolves file mounts by path, so it passes on a Mac or Windows laptop and fails on Linux, which is where it deploys. Identical hazard, and identical fix, to the console-edited list files below. Both halves are asserted rather than trusted: `TestUpstreamCredentialRotation` (e2e) rotates a real credential by rename against a running container, and `TestReReadFilesAreMountedAsDirectories` fails any compose file that mounts a re-read config file rather than its directory. |
| `FW_UPSTREAM_CA_BUNDLE` | *(empty)* | Absolute path to a PEM file of CA certificates, **appended** to the system roots for every TLS connection the firewall *makes* (registry, artifact CDN, deps.dev, scanner, approval). Set it when an enterprise TLS-inspecting proxy sits between the gate and the registry: without it every upstream handshake fails `x509: certificate signed by unknown authority` and nothing resolves. **Appended, never substituted** — the public roots stay, so a host reached *directly* (`NO_PROXY`, split-horizon DNS, a partially-inspecting proxy) keeps verifying normally; a firewall that replaced them would fail intermittently and per host, which is the worst shape a trust bug has. **"Bundle" means the full chain** — the root *and* every intermediate: a corporate proxy that withholds its intermediate is the "I added the root and it still fails" ticket, measured in `docs/TLS_INTERCEPTION.md` increment 6b. Refused **at startup**, before the listener binds, if the path is relative, the file cannot be read, holds no PEM `CERTIFICATE` block, or holds no CA certificate (usually the proxy's *leaf* instead of its issuer). On success the startup log names every anchor with its SHA-256 fingerprint in `openssl x509 -fingerprint -sha256` form, so you can compare it with what your estate distributed. Read **once**; rotating a corporate root is a restart. |
|  |  | ⚠️ **The proxy ADDRESS is not a `FW_` variable and deliberately never will be.** Use the standard `HTTPS_PROXY` / `HTTP_PROXY` / `NO_PROXY` environment variables — Go's HTTP client honours them, and that is the whole of our support for routing through a corporate proxy. A credential can ride in the URL (`http://user:pass@proxy:3128`), which works with no configuration of ours, but note it then reaches logs, `ps` and every error message; a first-class credential value is a separate decision, not yet taken. `NO_PROXY` is what keeps an internal registry or the scanner direct. Pinned by `TestPooledTransportHonoursTheProxyEnvironment` so a future change to the transport cannot quietly cost you the ability to chain. |
|  |  | 📏 **Why this exists when `SSL_CERT_FILE` appears to work.** Go also reads `SSL_CERT_FILE`, and measured on this image (`TestTheProductChainsThroughACorporateProxy`, legs P15-4/P15-5) it **keeps** the public roots and does get through a corporate proxy — not by contract, but because `crypto/x509` reads that file and then still scans `certDirectories`, where `distroless/static:nonroot` keeps its only bundle. That is an accident of the base image’s layout: the day `/etc/ssl/certs` stops holding the public bundle it becomes a **replace**, every host reached directly stops verifying, and you find out from a developer’s failed install. `FW_UPSTREAM_CA_BUNDLE` is the contract — validated at startup, anchors named in the log, appended by construction. The measurement is kept as a standing test so that day is a red pipeline rather than an incident. |

## Policy — what happens when the gate cannot simply allow

Every one of these defaults to the **safe** value, and an unrecognised value reads as the safe
value too, never the permissive one: a typo must not silently reopen a hole.

| Variable | Default | What it does |
|---|---|---|
| `FW_MODE` | `enforce` | **Whether verdicts are enforced at all.** `enforce` refuses; `report` computes and logs every verdict and then **refuses nothing** — the request is relayed and the counterfactual is logged as `REPORT MODE: WOULD HAVE REFUSED …`. This exists because nobody switches a blocking gate on in front of their build system cold: run `report` against real traffic for a week and read what it *would* have done, instead of taking our false-positive rate on trust. It changes only the **response** — the verdict, reason, audit record and queue entry are identical in both modes, which is what makes the numbers you collect predictive.<br><br>⚠️ **`report` suppresses policy verdicts, not request-integrity refusals.** An artifact whose path or filename does not address the package being judged, or whose URL signature is invalid, is still refused — those are not judgements about a package, they are the gate declining to serve a request whose two halves disagree, and relaying them would make `report` *less* safe than `enforce`. An operator evaluating the product must never be more exposed than one enforcing it.<br><br>The startup banner announces `report` in capitals and the console policy view reports it first, because a gate that is not enforcing while every dashboard is green is the worst state this product can be in. |
| `FW_UNSCORABLE_POLICY` | `block` | When no score can be obtained at all — no repo link, repo missing, scan failed. The common messy-metadata case. |
| `FW_UNVERIFIED_POLICY` | `closed` | When the deps.dev cross-check cannot *durably* confirm the package-to-repo link. **OCI**: deps.dev has no container index, so under `closed` every image that declares a source repo is refused as unverifiable (D48, #33) — set `open-with-visibility` to proceed on the self-declared repo with a log. Per ecosystem by construction: each instance fronts one ecosystem, so a Maven instance can run `open-with-visibility` while npm and PyPI instances stay `closed`. |
| `FW_BYTE_GATE` | `allow-but-log` | Whether artifact bytes are re-evaluated before being served, and what happens when that evaluation denies. `off`, `allow-but-log`, `enforce`. |
| `FW_UNKNOWN_PATH_POLICY` | `block` | A request the gate cannot name a package for and cannot justify as registry infrastructure. |
| `FW_WRITE_POLICY` | `block` | A request that would **write** upstream — push, publish, upload, delete. Yellow Jack is a pull-through gate. **Scoped to OCI today**, deliberately: npm mixes reads and writes on one surface. |
| `FW_MIN_RELEASE_AGE_DAYS` | `14` on npm, PyPI and Maven; `0` on OCI | Release **cooldown**, ON by default (D335; `0` turns it off). A release with no readable publish date is held while it is on, so an upstream that publishes no dates has EVERY package refused; on npm the gate says so once in its log, naming the upstream (D337). Measured cost at 14 days over benign npm, weighted by downloads: 7.39% of fresh resolves get an older release than upstream's newest, and 0.036% are refused outright because every version is held; a lockfile install is never held (E108). Measured benefit: 58.89% of single-poisoned-release attacks are held past their takedown (E30). releases newer than this are held back, so a resolver cannot land on a just-published version. Judged from the registry's own publish dates; a release with no readable date is held too. **How it is applied differs by ecosystem, and the difference is visible to developers** — see the note below. **npm/PyPI:** the release is filtered out of the metadata document (yanked-with-reason on PyPI; removed from the packument with `dist-tags` repointed on npm), so resolution walks to the next compliant version. **Maven:** the request is refused with the reason, because Maven has no per-version index to filter. **OCI: not applied, deliberately — see the note.** |
| `FW_MAX_RELEASE_AGE_DAYS` | `0` (off) | Release-age **floor**: the same window's other edge — releases *older* than this are held back, stopping a resolver silently downgrading to an ancient CVE-laden release. Same per-ecosystem coverage and behaviour as the cooldown above. |
|  |  | ⚠️ **The release window means different things to a developer in different ecosystems, and you should know which one they will hit.** On **npm and PyPI** a held-back release is filtered out of the metadata document, so the resolver quietly picks the next compliant version and the build succeeds — the window steers resolution. On **Maven** there is no per-version index to filter (`maven-metadata.xml` carries one `<lastUpdated>` for the whole artifact, not one per version), so the request is **refused** and the build fails with a reason saying when it will clear. Same policy, different developer experience: budget for the Maven one. Cost: while a bound is active, Maven spends one extra `HEAD` per artifact URL to read the repository's `Last-Modified`, memoised per URL. Both bounds default to `0`, and at the default there is no probe at all. |
|  |  | 🚫 **OCI is deliberately NOT covered, and this is a measurement, not a gap waiting to be filled.** The console's `/policy` page says so too: on a gate that cannot enforce the window, a non-zero value is shown as *NOT ENFORCED on oci* rather than as a bare number that reads like protection (`#150`). A container registry gives us nothing trustworthy to date an image by: the manifest response carries no `Last-Modified` (measured against Docker Hub), and the only timestamp in the pull path is `created` inside the image **config blob** — which is content the *publisher* uploads. Back-dating it and recomputing the digest yields a perfectly valid blob, so a cooldown keyed on it would be set by the party it restrains: any image could clear a 7-day cooldown the moment it was pushed. That is worse than having none, because you would believe your containers were covered. **And this is not a hypothetical attacker: legitimate images already do it.** Of 7 real images sampled on 2026-09-12, **4 report `created: 1970-01-01T00:00:00Z`** — every `gcr.io/distroless/*` one, because reproducible builds zero the timestamp on purpose so the same source yields the same bytes. One of those four is `gcr.io/distroless/static:nonroot`, which **this repository ships in four Dockerfiles**: a cooldown keyed on that field would compute our own base image as 56 years old and wave it straight through. Where a date *is* present it can also disagree with itself — `library/busybox:latest` reads `2026-05-20` in the index annotation and `2026-05-13` in the config, seven days apart, which is the width of a typical cooldown. **And where it is present and self-consistent, it still runs early**: across 18 Docker official images on 2026-09-16, compared against the registry's own push record, `created` was *earlier than the real push in 18 of 18* — median 3.5 h, maximum **1,041 days** (`busybox:1.36`) — with **4 of the 18 (22%) off by more than seven days** (`nginx:1.27` 55.5 d, `registry:2` 501 d, `traefik:v3.1` 14.6 d). Those four clear a 7-day cooldown the instant they land, with every publisher behaving honestly. So the field fails loudly on reproducible builds and quietly on mainstream ones. Covering OCI needs a new source of truth, not a new parser. ⚠️ **Docker Hub's own non-spec API does return a registry-set push time** (measured, anonymous) — but it is one registry's private endpoint, `registry:2` has no equivalent, and it lives on `hub.docker.com`, a *different host* from the registry, which would add an egress destination the interception mode deliberately avoids. See `whyOCIHasNoReleaseWindow` and issue #127. |
|  |  | 🔊 **Set one of these on an OCI gate and the gate tells you, twice, rather than staying quiet:** a `WARNING:` line in the startup banner naming the setting, its value and the gate, and `NOT ENFORCED` beside the value on `/policy`. It does **not** refuse to start: one environment file is often shared by several gates, and the value is meaningful for the others. Leave it off the image gate, as both shipped deployments do. |
| `FW_MALWARE_LIST` | *(empty)* | Absolute path to a newline-delimited feed of packages already publicly reported malicious (OSV / OpenSSF Malicious Packages). Build it with `sh scripts/dev.sh malwarefeed --src <osv-dir> --out <feed>` — the feed is a FILE, so the verdict costs **no egress**. **Re-read while the gate runs** (#160): refresh the file on your own schedule and the gate picks it up within a minute, with no restart. A failed or half-written re-read keeps the last good feed and says so on `/readyz`; an unreadable feed at STARTUP is still fatal. Absolute paths only (#38 / CVE-2025-64726). Package-wide advisories are enforced in every ecosystem; **version-pinned** advisories (the hijack case) are enforced in all four shipped ecosystems — PyPI at the `/simple/` index and `/_files/` gate, OCI on the reference, Maven on the request path, and npm by filtering the packument and judging the tarball filename (#103, #35). The startup log states the count for the running ecosystem. |
| `FW_MALWARE_FEED_KEY` | *(empty)* | Base64 **Ed25519 public key** the snapshot at `FW_MALWARE_LIST` must be signed with. Empty means **no verification**, which is what shipped before #157 and stays legal — refusing an unsigned feed would disarm layer 1 for every deployment that has not re-generated one. When it is set, the gate requires a detached signature **beside the feed** (`<feed>.sig`) and **refuses to load a snapshot that does not verify — at every re-read, not only at startup**, because the point of re-reading is that the bytes change afterwards. A refused snapshot never becomes the enforcing feed: the last good one stays in force and the failure is logged as a SECURITY line. A signed feed must also carry the header line `# yellowjack-feed v1 serial=N generated=<RFC3339> rows=N`, because a signature alone proves the key-holder produced those bytes **once** — which is exactly what a replayed snapshot also proves. The gate then refuses a re-read whose **serial goes backwards**, compared against the feed in force rather than a remembered maximum, so a deliberate rollback costs a restart and an attacker cannot do it quietly. A snapshot older than **72 hours** is logged loudly and still enforced: an old advisory is still an advisory, and refusing to enforce what we have because it is old would turn a stale feed into no feed. Generate a key with `go run ./scripts/feedsign -gen` and sign with `go run ./scripts/feedsign -key <private> -in <feed> -serial <n>`. **The key is yours** — a deployment that builds its own feed signs it with its own key, and nothing here implies trusting us. |
| `FW_MALWARE_FEED_URL` | *(empty)* | Where the gate **pulls the signed known-malware snapshot from, hourly**, off the request path (#157, D294). Empty means the gate fetches nothing and you keep `FW_MALWARE_LIST` current yourself, which is what shipped before. **There is no default**: every address the gate dials is your configuration (`docs/EGRESS.md`). Requires `FW_MALWARE_FEED_KEY` (an unverifiable pull is refused at startup) and `FW_MALWARE_LIST`, which is where it installs. The signature, header and row count are checked **in memory, before anything is written**, and the snapshot then reaches enforcement through the ordinary re-read within a minute. A snapshot older than the one in force is refused; the same one is not rewritten. A failed pull keeps the feed in force, is logged once per change, and **never makes a replica unready**. ⚠️ **Mount `FW_MALWARE_LIST`'s DIRECTORY writable** (the gate replaces the file by rename), and **seed it with a signed snapshot** (in the image, or by an init container): a replica that starts with no file tries one pull and refuses to start if it fails, so an unseeded replica cannot start while the endpoint is down. The registry credential (`FW_UPSTREAM_AUTH*`) is never sent to this host. |
| `FW_ALLOW_LIST` | *(empty)* | Absolute path to the **operator's own** allow list: one package name per line, `#` comments. A listed package is served **without scoring** and without any upstream call, so it keeps working while deps.dev is down or throttling. ⚠️ It does **not** override `FW_MALWARE_LIST` — a published advisory still refuses the package, and the startup path logs the conflict by name so the allow list does not look broken. |
|  |  | **An allow line may name ONE RELEASE**, in the same spellings the deny list takes, plus `image@sha256:…` for OCI (a digest, never a tag — a tag is mutable, so "allow whatever this tag points at next" is not a decision anyone made). **A release named here outranks a known-malware advisory naming the same release** (D312): the administrator looked at that artifact and decided. It is loud, not silent — the log line `[administrator-override]`, the audit record's `override` field and the console all carry it, so the organisation sees which allows were made over a finding. ⚠️ **A bare name does NOT override an advisory**: it would extend the administrator's judgement to releases that did not exist when they made it. The refusal says so and names the pin to write instead. The override also needs a KNOWN version (a request we cannot attribute to a release is refused), and **your own deny list still wins**. It does not apply to an advisory that condemns EVERY version of a package: that verdict is reached before any release is named, and the log says the entry could not be applied rather than ignoring it. |
| `FW_DENY_LIST` | *(empty)* | Absolute path to the **operator's own** deny list, same format. A listed package is refused with no upstream call and a reason that names *your organisation* as the decider rather than an advisory — a developer must be able to tell "we blocked this" from "this is publicly reported malware", because they go to different people (D193). Enforced as a **hard** deny, so a lockfile-pinned tarball fetch cannot walk past it (#11). |
|  |  | 🔄 **Which file-valued settings are re-read, and which need a restart.** Re-read while running: `FW_MALWARE_LIST` (within a minute), `FW_ALLOW_LIST` and `FW_DENY_LIST` (within 5 s), `FW_UPSTREAM_AUTH_FILE` (within 1 s). Read ONCE at startup, so a change needs a restart: `FW_UPSTREAM_CA_BUNDLE` and `FW_INTERCEPT_CA_FILE` — both are trust material verified at boot (the interception CA has a startup preflight), and swapping the chain under a running listener is a posture change rather than a refresh. In every re-reading case a failed read **keeps the last good value**: blanking a deny list or a feed would fail OPEN. |
|  |  | 📋 **What the console shows of a list is a REPORT, not the list.** Each gate reports at most 200 names per list in its heartbeat, and if the whole report would not fit the heartbeat budget it sends each list's digest and count **without the names** — a heartbeat the control plane refuses would make a healthy gate read as stale, and liveness is not worth trading for a display (`#139`). The `/policy` page then says how many entries are loaded and enforced, and why their names are not shown. **Enforcement is unaffected either way:** the gate always matches against the full file, and the digest that detects replicas disagreeing is computed over the full list. |
|  |  | ⚠️ **On OCI, an entry covers the WHOLE repository — every tag — even when it names one.** `library/alpine:3.19` and `library/alpine` are the same entry here: the reference is part of an image's identity (so the line is well formed and IS enforced), but matching strips it, because a published advisory has to condemn a repository whichever tag was asked for. The trap is the accidental one — blocking the single bad tag of a base image your builds depend on takes out **every** build using any tag of it, and the refusal names the repository, so the log reads exactly as though you had written the repository. The gate now says so when it loads the file rather than leaving you to find out from a failed build; per-tag operator entries are not supported. Other ecosystems refuse a version-pinned line outright. |
|  |  | **A line may name ONE RELEASE instead of the whole package** (#155), in each ecosystem's own spelling: `lodash@4.17.20`, `@scope/name@1.2.3`, `requests==2.31.0`, `group:artifact:1.2.3`. That release is refused and its siblings stay installable — the hijack case, where one version of a package you depend on is bad and the package is fine. A bare name still means every version. Enforced wherever the release is knowable: the npm packument and tarball, the PyPI index and file, the Maven request path. If a request's version cannot be determined and the package carries a version-scoped entry, it is refused rather than guessed at. **OCI is the exception**: an entry there names a tag or digest and applies to the whole repository (#128), unchanged. **ALLOW entries are name-only** and a version on an allow line is refused at startup, with a message saying so. |
|  |  | 🛡️ **The deny list is your dependency-confusion defence, and it is the only one we can give you.** Put the names of your **internal, never-published packages** in `FW_DENY_LIST`. Then a public package that appears under one of those names is refused at the gate, with your organisation named as the decider — which is the whole attack: someone publishes `your-internal-lib` to the public index and a resolver prefers it. We cannot detect this for you from public data. A private name is, by construction, absent from every public index and popularity list, so nothing computable from the outside distinguishes "an internal name someone squatted" from "a new package" — but *you* know your namespace, and this is where you tell us. Keep the list in the same place you keep the list of what you publish internally, so the two cannot drift apart. **Measured on PyPI as well as npm (2026-09-12):** the strongest public-data instrument for this, a name-distance rule, reaches 6.5% of typosquats at 0.85% benign at its tightest and, of the packages squatting *private* names, 2 of 15 — the name it would have to be near is in no public list. On PyPI this list is not a fallback for a detector we lack; it is the mechanism. |
|  |  | ⚠️ **If the console edits these lists (`CONSOLE_LIST_REPO`), bind-mount the list files’ DIRECTORY into the gate — never the two files.** A file bind mount pins that file's *inode*; the console writes atomically (temp file, then rename), so an edit replaces the inode and a container holding a file-mount goes on reading the old one **forever**. The failure is silent and total in the worst direction: the console reports “committed and pushed”, `git log` is perfect, and the gate enforces none of it. It is also **platform-masked** — Docker Desktop resolves file mounts by path, so this passes on a Mac or Windows laptop and fails on Linux, which is where it gets deployed. `e2e/async_local.sh` leg 23 pins it by pulling a real package after the edit. |

## Caching and limits

| Variable | Default | What it does |
|---|---|---|
| `FW_SCORE_CACHE_TTL` | `1h` | How long a score is cached in memory — the L1 fan-out guard. `0` disables L1 caching, and is the single spelling for "off". 🛡️ **An OCI tag is not trusted from this cache by name.** A tag is mutable, so on every pull the gate asks the registry what the tag points at now (one `HEAD`, no body) and uses the cached verdict only for that exact digest; a moved tag is re-evaluated on its first pull (#93, D164). Cost: one request per warm tag pull, on an anonymous registry and, after the first pull, on one that demands a bearer token (the token is kept per image for the lifetime the registry states); none for a pull by digest. |
| `FW_SCORE_CACHE_MAX_ENTRIES` | built-in default | Caps entries in **each** L1 cache. A TTL alone is not a bound: cardinality grows without limit in a long-lived service. `0` means "use the default", never "unbounded". |
| `FW_SCORE_L2_TTL` | `0` (never stale) | Freshness window for the **durable** L2 score cache. Without it a score is remembered forever — an unexpirable trust cache. Past this window the repo is treated as cold and re-scanned rather than served stale. |
| `FW_MAX_CONNS_PER_HOST` | built-in default | Bounds the TCP connections the firewall opens to any one host. |
| `FW_RATELIMIT_BACKOFF_TTL` | `10s` | How long a package stays backed off after a scoring probe was rate-limited (HTTP 429). The same duration governs the deps.dev OUTAGE breaker: after a deps.dev lookup fails as unreachable or 5xx, verification answers "unavailable, retry" for this long without re-probing, so an outage costs one timeout rather than one per cold package (D342). `0` disables both. |
| `FW_FLOW_FLUSH_INTERVAL` | `1m` | Capacity flush cadence, and the bucket width. |

## The approval service's own variables

The approval service holds the durable state: the approval queue, the L2 score cache,
and the append-only decision log the #28 compliance export reads.

| Variable | Default | What it does |
|---|---|---|
| `APPROVAL_LISTEN_ADDR` | `:8090` | Address the service listens on. ⚠️ **`:8090` is every interface, and this service has no authentication** — `PUT /v1/decisions` approves a quarantined package, `PUT /v1/scores` writes a score the firewall then serves as a verdict. Note the asymmetry with `CONSOLE_LISTEN_ADDR`, which defaults to **loopback** precisely so an unauthenticated operator surface is not published by accident: the service that merely *displays* the queue is bound more carefully than the one that can *approve* things in it. The shipped `docker-compose.yml` also publishes `8090` to the host. Authentication here is **decided, and the decision is not to build it** — **D77** (2026-07-27) rules inter-service auth out of the application and onto the deployment's service mesh or network policy, so #13 closed with its forgery half shipped (the scan-result capability token) and its mechanism half declined. This line previously read *"deferred, not decided — the project's call (#13 item 2, D31 Q3)"*, which was true when written and stale from the day D77 landed. **The practical instruction is unchanged and now load-bearing rather than provisional:** network reachability IS the only control here, by design, so scope it accordingly — see `docs/SETUP.md`, "these services trust the network between them". The exposure stays enumerated and pinned by `approval/exposure_test.go`, which is what keeps a delegated boundary visible instead of assumed. |
| `YJ_CONTROL_PLANE_BIND` | `127.0.0.1` | **Compose-level, not read by any service** — it is the host interface `docker-compose.yml` publishes the approval service (`8090`) and the scheduler (`8096`) on. Setting it to `0.0.0.0` publishes an **unauthenticated, mutating** control plane on every interface, which removes the single-host protection D77's private-network assumption leans on. `e2e/async_local.sh` and `e2e/verify_repo_local.sh` export `0.0.0.0` deliberately, because their stacks live in a throwaway network the rig tears down; that is not a pattern to copy into a deployment. It is documented here rather than caught by the drift guard below because the guard reads Go source for `FW_*` lookups, and this variable is interpolated by compose and never reaches Go at all — so nothing but this row can surface it. |
| `POSTGRES_PASSWORD` | *(none — generated)* | **Required, and deliberately not defaulted (#22).** Consumed twice by `docker-compose.yml`: by the `postgres` service, and interpolated into `APPROVAL_DATABASE_URL` so the two cannot drift apart. It used to read `postgres` in both places — one identical database credential on every installation of the product, in the file a self-hoster runs unmodified. `sh scripts/dev.sh up` generates a per-machine value into a git-ignored `.env` (`scripts/gen-env.sh`), so "runs with nothing set" still holds for a developer; a fresh clone that skips that step gets compose's own error naming the command, not a silent default. ⚠️ **Postgres applies this only when it initialises an EMPTY data directory**, so changing it does nothing to an existing `pgdata` volume — the generator detects one and keeps the legacy value rather than locking you out. Rotating means `docker compose down -v`, which destroys the local database and any audit trail in it. The e2e rigs export a fixture value instead, which `docker-compose.e2e.yml` documents as a fixture rather than a secret. |
| `APPROVAL_DATABASE_URL` | *(empty — in-memory)* | Postgres DSN. **Empty is not a broken deployment**: the service starts with an in-memory store and works, which is what keeps "runs with nothing set" true for the whole stack. It is lost on restart, so it is right for local development and wrong for anything holding an audit trail. This is the one variable a real deployment must set, and it is required for *durability*, not for *startup*. |
| `APPROVAL_DB_CONNECT_TIMEOUT` | `60s` | How long startup keeps retrying the FIRST database connection before giving up; `0` means one attempt. Exists because an orchestrator does not promise start order: the first real `helm install` started this service before the postgres Service name resolved, and it exited and restarted five times. Bounded on purpose -- after the window the last error is returned and the process exits with it, so a wrong DSN is still discovered at startup rather than becoming a pod that is Running and never Ready. Every failed attempt is logged with its error. |
| `APPROVAL_UPSTREAM_ECOSYSTEM` | `npm` | Which package-manager protocol the developer-lookup page speaks when harvesting the registry's own metadata (D158). `npm`, `pypi` and `maven` are implemented; **`oci` is not, and deliberately** — a registry publishes no push time (the only date is `created` inside the publisher-uploaded config blob, demonstrated forgeable; see `whyOCIHasNoReleaseWindow`), so an OCI harvest would render a date the publisher chose. Any other value means no harvest. Selecting an ecosystem is not enough on its own — the matching URL variable below must also be set, or the page reports "not collected by this service". |
| `APPROVAL_UPSTREAM_NPM` | *(empty — no harvest, no outbound call)* | Base URL of the npm registry to read package metadata from for the lookup page. **Empty is the shipped default and makes no network call at all**: the page reports the field as "not collected by this service", exactly as before this feature existed. Defaulting it to `registry.npmjs.org` would give every existing deployment a new egress destination it never asked for, against the zero-egress posture (D155, D26). An air-gapped or mirrored deployment points this at the same internal mirror the firewall uses. |
| `APPROVAL_UPSTREAM_PYPI` | *(empty — no harvest, no outbound call)* | Base URL of the **PyPI JSON API** to read project metadata from for the lookup page — `https://pypi.org/pypi` for the public index, or the same path on a mirror (devpi and pypiserver both expose it). **Not** the `/simple/` index: that is the installer protocol (PEP 503, a bare link list) and carries none of the fields this page renders, so a fetcher pointed at it would return an empty harvest that reads as a healthy package. Empty is the shipped default and makes no network call, for the same zero-egress reason as the npm variable above. Deliberately a **separate** variable: an operator running an internal npm mirror has not thereby authorised calls to a Python index. |
| `APPROVAL_UPSTREAM_MAVEN` | *(empty — no harvest, no outbound call)* | Base URL of a **Maven repository root** to read artifact metadata from for the lookup page — `https://repo.maven.apache.org/maven2` for Central, or the same path on a Nexus/Artifactory proxy. Empty is the shipped default and makes no network call, for the same zero-egress reason as the two variables above, and it is separate for the same reason: an internal npm mirror is not authorisation to call a Java repository. **Costs one extra request per lookup, and the reason is recorded rather than hidden**: `maven-metadata.xml` carries one `<lastUpdated>` for the *whole artifact* (guava: 158 versions, one timestamp), so dating a version by it would stamp every version identically while looking correct. The honest date is the per-file `Last-Modified` the **repository** sets, which needs a `HEAD` on the release POM — the same source, and the same measurement, as the Maven release window (`mavenage.go`). A repository that forbids `HEAD` or serves no `Last-Modified` simply yields no date; the rest of the page still renders. **Two fields Maven cannot answer at all:** there is no deprecation signal (no equivalent of npm's `deprecated` or PyPI's PEP 592 yank), and no publisher list (`<developers>` is publisher-authored prose inside the artifact, not the repository's record), so both render empty. |
| `APPROVAL_FLOW_RETENTION` | `336h` (14 days) | How long per-package flow/usage buckets are kept before the sweeper deletes them (#32 Phase C). This is the telemetry dataset, deliberately separate from the audit log — the audit log is append-only and is **not** swept by this. |
| `APPROVAL_FLOW_SWEEP_INTERVAL` | `1h` | How often the retention sweep above runs. |
| `APPROVAL_ALERT_SWEEP_INTERVAL` | `1m` | How often the service checks for conditions worth emailing about. |
| `APPROVAL_FP_WEBHOOK` | *(empty — reports stay local)* | Where to **forward** false-positive reports filed from the console (`#142`), as one JSON `POST` per report. Empty means a report is recorded on this control plane and **nothing leaves the deployment** — the shipped default, and asserted by a test with a negative control. Set it to an `http(s)` URL you run (an inbound webhook on your chat tool, a ticketing system, a collector inside your own boundary): there is no built-in destination and no vendor host. A destination that is down never costs the local record — the report is stored first, forwarding is best-effort, and failures are logged once per change of outcome. |

The console is a stateless HTTP client of the approval service. It owns no data.

| Variable | Default | What it does |
|---|---|---|
| `CONSOLE_LISTEN_ADDR` | `127.0.0.1:8085` | Address the console listens on. **The default is loopback, not `:8085`**, and that is the deliberate choice: the console has no authentication unless the two variables below are set, so a default that bound every interface would publish an unauthenticated operator surface to the network the moment someone ran it. |

The two go together: widening the bind address without setting these is the mistake this table exists to make visible. Fuller auth is deferred (D58); see #13. |
| `CONSOLE_LIST_REPO` | *(empty — editing off)* | Absolute path to a **git working tree** holding the operator allow/deny list files. Empty means `/lists` renders read-only. Relative by design — a path escaping the repo is refused, because a write outside the repository is a write outside the audit trail that is the whole reason this mechanism was chosen. Point `FW_ALLOW_LIST` at the same file as it appears on the firewall's filesystem. |
| `CONSOLE_LIST_DENY_FILE` | `deny.txt` | The deny list's path inside `CONSOLE_LIST_REPO`. Same rules as above; pairs with `FW_DENY_LIST`. |
| `CONSOLE_LIST_ECOSYSTEM` | `npm` | Which ecosystem's naming rules apply when validating an entry an operator types. Must match the gated deployment's `FW_ECOSYSTEM`: it decides whether `library/nginx:1.25` is a well-formed name (it is, for `oci` — D164) or a version pin the firewall would refuse to start on. |
| `CONSOLE_LIST_REMOTE` | `origin` | Where a list change is pushed after it is committed. Empty means **commit only** — legitimate for a single-host deployment, and reported as such on the page rather than presented as a change that has reached the fleet. A failed push does not fail the edit: the commit stands, and the operator is told the difference. |

## The scanner's variables

The scanner is a **run-once** container: it scans one repo, POSTs the result, and exits.
It serves nothing and has no port. These are set by the scheduler at `docker run` time
rather than by an operator, but they are part of the surface and are listed for the same
reason as everything else — someone debugging a scan needs to know what it read.

| Variable | Default | What it does |
|---|---|---|
| `SCANNER_REPO` | *(none — **required**)* | The source repo to scan. The one genuinely required variable in the whole surface, and it is required of a container the scheduler starts, not of an operator. |
| `SCANNER_SINK_URL` | *(none — **required**)* | Where to POST the result. Same note as above. |
| `SCANNER_SCORECARD_BIN` | `scorecard` | Path to the OpenSSF Scorecard binary. The image sets this to an absolute path, because distroless has no `PATH` search to fall back on. |
| `SCANNER_SCAN_TIMEOUT_SECS` | `180s` | Bound on the Scorecard run. Shorter than the scheduler's timeout on purpose (see above). |

## The cache service's variables

⚠️ **The cache is out of scope permanently (D151).** We integrate with an existing
registry — ECR/CodeArtifact, Harbor, Nexus, Artifactory — rather than writing one. This
service still exists in the tree and still has a settings surface, so it is enumerated
here; it is not a component to build on.

| Variable | Default | What it does |
|---|---|---|
| `CACHE_LISTEN_ADDR` | `:8070` | Address the cache listens on. |
| `CACHE_UPSTREAM` | `http://localhost:8080` | The firewall it sits in front of. |
| `CACHE_TTL` | `5m` | How long a cached response stays fresh. |
| `CACHE_MAX_BYTES` | `268435456` (256 MiB) | Total body+header budget across all entries, so the cache cannot grow without bound. |

## Variables that are not ours

| Variable | Read by | What it does |
|---|---|---|
| `GITHUB_TOKEN` | scanner, scheduler | Raises the GitHub API rate ceiling for Scorecard. ⚠️ **A credential.** Unset works but hits anonymous rate limits quickly, which surfaces as scans that fail for a reason unrelated to the package. Named without a `YJ_`/`FW_` prefix because it is the variable Scorecard and the GitHub tooling already expect. |

## Reading this as an operator

- **You can run it with nothing set.** Start there, then change one thing at a time.
- **The policy section is the one with teeth.** Everything in it fails safe by default; each
  change is a deliberate loosening with a stated reason.
- **`0` means different things by design, and they are not interchangeable.** For TTLs it means
  *off*. For `FW_SCORE_CACHE_MAX_ENTRIES` it means *use the default*, because a zero cap meaning
  "cache nothing" would silently disable caching in every hand-built config predating that field.
- **Nothing here is read from disk, from your working directory, or from a package we inspect.**
  See [CONFIG_SURFACE.md](CONFIG_SURFACE.md).
